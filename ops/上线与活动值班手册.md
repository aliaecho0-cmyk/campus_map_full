# 百团大战：上线、容量验收与活动值班

适用域名：`https://www.clubfairmap.com/`。用户确认域名购于腾讯云、服务部署于阿里云香港。用户提供的控制台截图显示：香港 D，`ecs.u1-c1m2.xlarge`，4 vCPU / 8 GiB，Ubuntu 22.04，40 GiB ESSD AutoPL 系统盘，按流量计费、公网带宽上限 100 Mbps；活动需要面对至少 2000 人的高峰。以上是截图信息，尚未登录服务器复核。实际端口、数据库路径、进程管理方式、反向代理链路和可用带宽均待现场确认。域名注册商不决定服务器承载能力。仓库旧 `deploy.md` 的 IP、端口、目录不可直接套用。

## 1. 先取得现场事实

由服务器同学把本 `ops/` 目录放到服务器后，用普通应用用户运行：

```bash
bash ops/inspect-server.sh
```

脚本只读取系统信息；不会安装软件、读取 `.env`、显示进程参数或环境、重启进程、修改配置、执行压测。确认实际后端端口和 PID 后可添加 `--backend-port 数字 --backend-pid 数字`；只发一次本机 `/api/auth/me` 请求，未登录的 `401` 是预期结果，不能据此认定数据库正常。该请求可能产生正常访问日志。

确认数据库真实绝对路径后，可加 `--database /实际绝对路径/database.db`。这里只读文件信息和 100 字节文件头，不通过 SQLite 打开在线数据库。需要查表结构时，另提供管理员确认已经完成、无人使用的独立在线备份产物：`--schema-snapshot /备份绝对路径/backup.db`。不能把在线数据库填到这个参数，也不能把正在复制的文件或未经协调复制的 `.db` 文件当作完整备份；它采用 immutable 只读连接，忽略在线 WAL，并拒绝附带 WAL/SHM/journal 文件的备份。表结构输出不含业务数据。[SQLite immutable 参数限制](https://www.sqlite.org/uri.html#uriimmutable)

Nginx 检查只提取常见目录的部分指令，无法解析所有 include 或继承；没有输出不代表未配置。无需为巡检脚本自动提权。分享结果前检查目录名、用户名等是否需要打码，勿附 `.env`、JWT、口令、私钥或真实领取码。

还需从控制台记录最近带宽峰值、磁盘剩余容量及延迟，并复核上述截图配置；从组织方确认 2000 人是否会集中在同一分钟打开、每人交互频率、预估同时兑奖工作人员数。CPU 很空也可能被带宽限制；“在线人数”与“每秒写入请求”不能混用。

## 2. 分工与交付标准

| 负责人 | 必须完成 | 可核验的完成标准 |
|---|---|---|
| 前端同学 | 先显示地图再加载登录/奖励状态；网络超时后可恢复；减少首屏图片/字体/音乐下载；图片合理压缩和按需加载 | 后端不可达时仍能看地图、点开已内置社团信息；提示稍后重试；音乐不阻塞首屏；普通手机校园网实测 |
| 后端同学 | 严格校验摊位 ID；按设备/业务身份限制重复写入；正确处理忙等待；统一迁移与运行数据库路径；就绪检查和结构化错误 | 相同浏览不重复计奖励；同码并发核销只成功一次；启动遇空库/缺表就明确报错；错误无口令/领取码；数据库异常不会产生成功假象 |
| 服务器同学 | 静态资源缓存与文本压缩；确认带宽；后端仅本机可达；单进程托管自动重启；HTTPS 续签；备份恢复；监控与日志轮转 | 公网不开放后端端口；实际 Nginx 配置验证后平滑加载；带宽图和报警可看；隔离环境完成恢复；重启恢复演练 |
| 组织负责人 | 明确峰值目标、活动时间、奖品规则、值班联系人、降级决策和隐私/授权 | 有唯一值班群和拍板人；现场网络预演；电子核销不可用时有防重领的人工登记办法 |

SQLite 当前为同步本地数据库。先用一个后端进程验证目标负载，不通过盲目增加 PM2 实例来承诺扩容。是否启用 WAL、调整事务或迁移数据库应由后端同学在隔离库验证，启用 WAL 不会让 SQLite 同时有多个写入者。

## 3. 访问链路与 Nginx 调整

正常链路应清楚记录为：手机 DNS → 域名 HTTPS 入口 → Nginx 静态网页；其中 `/api/` → 本机后端 → 本地数据库。若经过 CDN 或其他代理，把这一跳也写入现场记录，并确认真实客户端地址只信任已知代理。

下面只是指令示例，不是完整可直接覆盖的站点配置。先检查现有路由、其他站点、证书及 include；替换实际端口，合并到对应上下文。修改后由管理员执行 `nginx -t`，通过才平滑重载。生产失败即回到原配置。

```nginx
# http 上下文：仅在确认现有 gzip/upstream 配置后合并。
gzip on;
gzip_vary on;
gzip_min_length 1024;
gzip_types text/css application/javascript application/json image/svg+xml;

upstream campus_backend {
    server 127.0.0.1:YOUR_CONFIRMED_PORT;
    keepalive 32;
}

# 以下放入现有 HTTPS server；保留正确的 root 和证书配置。
location ^~ /api/ {
    # 不带 URI 后缀，保留 /api/... 路径。
    proxy_pass http://campus_backend;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_connect_timeout 3s;
    proxy_read_timeout 15s;
    proxy_send_timeout 15s;
    proxy_cache off;
    proxy_hide_header Cache-Control;
    add_header Cache-Control "no-store" always;
}

# 只有经过确认、全部由构建器生成内容哈希文件名的 /assets/ 才适用。
# 若这个目录混有固定名称文件，缩小此规则的范围；错误页不设置一年缓存。
location ^~ /assets/ {
    try_files $uri =404;
    add_header Cache-Control "public, max-age=31536000, immutable";
}

location = /index.html {
    add_header Cache-Control "no-cache" always;
}

location / {
    try_files $uri $uri/ /index.html;
    add_header Cache-Control "no-cache" always;
}
```

不要假设旧版 Nginx 已默认启用上游 HTTP/1.1 保活；示例显式配置。[Nginx 上游保活官方说明](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#keepalive) 不要机械套用 `worker_connections`：同时受服务文件句柄限制、连接方式、上游连接和 CPU/带宽制约。增加参数不等于增加实际容量。已有 CDN 时，还要确认 CDN 不缓存 `/api/` 和用户状态，不能只改源站。

`add_header` 的继承规则会受 Nginx 版本影响，新增 location 级缓存头可能使 server 级安全头不再继承。合并示例时逐项保留已有安全头，并通过响应实测验证。[Nginx 响应头继承说明](https://nginx.org/en/docs/http/ngx_http_headers_module.html#add_header) 压缩优先针对公开文本；涉及秘密且同时回显用户输入的动态响应，应单独评估压缩策略。不要压缩已压缩的音频和图片来浪费 CPU。

校园网常有多人共用出口 IP。不要先给全站设置“每个 IP 每秒 1 次”一类小阈值，可能把正常学生一起拦掉。浏览写入优先按设备/业务身份限流、去重；敏感登录接口结合身份与 IP 做宽容的防滥用策略；实际阈值用正常访问数据验证。

## 4. 容量验收只在隔离环境进行

用户给定至少 2000 人的高峰目标，但到达窗口和交互频率尚未给定。以下是按 2000 人制定的验收场景与建议门槛，不是已经达到的保证。

1. 建立与生产 4 vCPU / 8 GiB 规格、Node/Nginx 版本、静态资源和代理配置一致的测试环境，使用独立域名/端口、独立密钥与人工合成数据。压测客户端在另外一台机器上，经测试域名访问该隔离环境，涵盖 TLS 和 Nginx；不是从服务器本机回环请求。测试程序须明确指向这个环境。不要直接运行仓库旧压测脚本去请求当前生产域名或生产库。
2. 准备预计活动规模的历史记录。不要仅用空库或小副本测一次本机 HTTP 就下结论。测试同一码争抢、同一设备重复浏览、跨设备并发、新用户登录和正常查询。
3. 用预期峰值的 25%、50%、100% 分档增加负载，每档至少 5 分钟；在目标负载持续 30 分钟，再短时测试 2 倍请求到达速率。压测机独立运行，记录实际每秒请求数和连接数；压测机饱和或被自身连接数限制时结果作废。
4. 将读静态资源、登录、浏览写入、状态查询、领取码和工作人员核销按真实流程混合。用 `写入请求/秒 ≈ 活跃用户数 × 每人每分钟提交次数 ÷ 60` 估算：2000 人每分钟各提交一次约 33 次/秒，每 30 秒一次约 67 次/秒，每 10 秒一次约 200 次/秒。分别测试这些场景，并叠加实际查询和登录请求。2000 人在 60 秒内登录，单是登录到达速率又约 33 次/秒；若一次用户操作触发多个 API，应逐项计入。
5. 每档记录成功率、超时、HTTP 429/5xx、95%/99% 响应时间、CPU/内存、磁盘延迟、DB busy/locked、Node 重启、出口带宽。出现错误持续增长、内存持续攀升或响应时间失控即停止升压并定位。
6. 建议目标：目标负载下合法业务请求成功率至少 99.9%，不出现重复核销或丢进度；API 95% 响应小于 1 秒、99% 小于 3 秒；普通手机从校园网首次进入 3 秒内可用。具体门槛需按活动需求和校园实网基线修订。CPU、磁盘、带宽须留余量，并能解释突发后的恢复行为。
7. 在线真实验收只安排少量同学从不同校园出口/手机运营商正常使用，覆盖首次打开、二次打开、断网恢复、扫码兑奖；不向生产站点发送未经协调的高并发流量。

带宽应单独核算：每秒新增访客数 × 每人冷启动下载字节数 × 8 是理想化的出口 bit/s 需求，还不含协议开销；浏览器缓存不会帮助第一次扫码进入的同学。以十进制 MB 为例：2000 人在 60 秒内首次进入，每人只下载 1 MB，就需要约 `2000 × 1 × 8 ÷ 60 = 267 Mbps`，已超过截图的 100 Mbps 上限；每人 3 MB 则约需 800 Mbps。在理想、独占且能跑满的 100 Mbps 出口上，2000 份 1 MB 合计也至少需要 160 秒才能传完，这不是每个人各自的固定等待时间。实际还会受到协议、共享出口和跨境链路影响，100 Mbps 上限不等于到校网络保证带宽。

因此先测冷启动实际传输量、减少首屏资源，再决定是否升级出口或使用 CDN。若整页压缩后仍达数 MB，不能仅凭 4 核 8 GB 承诺 2000 人一分钟内打开都流畅。未备案香港站点若选 CDN，应仅评估服务商允许接入的境外加速区域；不能直接启用中国内地节点或声称无需备案。境外 CDN 到校园是否更快必须用实际校园网络测试，正式购买前依据结果选取。

## 5. 备份、恢复与发布

- 后端同学先确定唯一的数据库真实路径，迁移、备份、运行进程都使用它。发布前保留当前代码版本、配置的安全副本和可恢复的数据库在线备份。
- 控制台截图显示未开启实例释放保护，系统盘随实例释放。服务器负责人应确认到期、费用与释放流程，并保证备份不只存在这块系统盘上。本手册不会更改控制台开关；是否开启释放保护由有管理权限的负责人按运维流程决定。
- 使用 SQLite Backup API 或 SQLite 官方 `.backup` 方式生成完整备份；保存于非网页根目录，限制权限，发送到受控的异机存储。频率按可接受数据损失量决定，例如希望最多丢 5 分钟就需设计并验证对应备份/恢复策略，不能承诺仅靠每天备份做到。[SQLite 在线备份机制](https://sqlite.org/backup.html)
- 不把运行中单独复制 `.db` 当成一致性备份；WAL 模式下尤其不能忽略事务状态或自行拼接一组 `.db`/`-wal`/`-shm` 文件。
- 恢复演练必须用隔离目录和独立进程：恢复备份，检查表结构/完整性和活动数据，再以测试身份走一次浏览、领码与核销。记录备份时间、恢复耗时和核销去重结果。未验证恢复的备份不能视为完成。
- 生产恢复由值班负责人决策：停止接受新写入、保留故障现场、恢复到确认的数据点、校验后开放。恢复旧库会回退最近核销记录，必须对照现场发奖登记补齐，防止重领。
- 发布静态资源时保留旧的哈希资源一段时间，避免已打开页面加载旧资源失败。数据库变更先在隔离库验证；代码回滚不能自动回滚数据库结构或已经发生的兑奖事实。

## 6. 活动当天监控与降级

活动前固定一位总负责人、一位服务器值班、一位后端值班、一位前端值班。监控至少覆盖域名 HTTPS 访问、5xx/超时、Node 重启、内存和磁盘、DB locked/busy、出口带宽与证书有效期；日志轮转需确认已生效，日志中不得记录登录口令、JWT、完整领取码。

外部首页探测应低频；若增加数据库就绪接口，应只读、无业务数据泄露、短超时，并限制暴露细节。告警按正常基线设定，建议预警参考：错误率高于 1% 持续 2 分钟、95% 响应超过 2 秒持续 5 分钟、带宽持续超过上限的 80%、磁盘剩余少于 20%、服务反复重启。它们是初始建议，不能替代活动目标和实测调整。

出现拥塞时先判断是资源下载、校园链路、后端队列还是数据库锁。地图应能维持只读浏览；可以暂停非必要音乐或进度刷新。核销失败或超时必须查询最终状态后再决定是否重试，不能把网络超时当成“没有核销”。如果电子核销不可恢复，按预先批准的人工登记流程发奖并保留防重领依据；不要临时取消全部校验。

完成标准：控制台配置和峰值目标有记录，测试环境达到约定指标，校园实网验收通过，备份恢复演练有结果，值班人知道何时降级和怎样恢复。未拿到这些证据前，不能说“服务器肯定不会卡或崩”。
